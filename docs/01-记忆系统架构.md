# 01 · 记忆系统架构

> 记忆写入 → 自动向量化 → 混合召回 → 防幻觉门控 → 事实层兜底

---

## 一、问题拆解

我把「大模型没有长期记忆」拆成三个可独立攻克的子问题：

| 子问题 | 用户视角 | 对应模块 |
|---|---|---|
| 记不住 | 「我昨天说的它全忘了」 | 记忆写入 + 向量化 |
| 想不起 | 「它记了但该用的时候调不出来」 | 混合召回 |
| 不敢说 | 「它为了接话，编了一件没发生的事」 | 防幻觉门控 |

---

## 二、记忆写入

### 存在哪

核心表 `memory_records`，存在 Supabase (PostgreSQL) 里。每条记忆有以下关键字段：

```
id          -- 主键
content     -- 记忆正文
source      -- 来源分类（见下方）
role        -- 谁写的
created_at  -- 时间戳
```

### 来源分级（source）

不是所有记忆都一样重要，按来源分级：

| source | 含义 | 可信度 |
|---|---|---|
| `conversation` | 对话中手动标记的重要时刻 | 最高（人工确认）|
| `session_digest` | 摘要器自动提取，经人工审核批准 | 高（机器提取 + 人审）|
| `early_diary` | 早期手写日记（系统冷启动阶段） | 高 |

### 为什么要分级

这是记忆系统和「把聊天记录全存下来」的本质区别。全存会导致：
1. 噪声淹没信号——日常闲聊和关键时刻混在一起，检索质量下降
2. 成本失控——向量化和检索都有算力开销
3. 幻觉素材增多——低质量记忆被召回时，模型更容易脑补

所以我选择**精选写入**：只有经过确认（手动标记或摘要审核）的内容才进记忆库。

### 摘要器：从对话到记忆的桥梁

不可能每句话都手动标记，所以有一个自动摘要器（SessionDigestService）：

1. 按对话轮次计数，攒够 N 轮（默认 30）且距上次提取间隔足够时触发
2. 用一个成本较低的模型提取这段对话的关键信息，生成摘要草稿
3. 草稿写入 `memory_digest_drafts` 表，状态为 `pending`
4. **人工在审核页面决定批准或丢弃**——这一步是质量闸门
5. 批准后写入 `memory_records`，source 标为 `session_digest`

草稿 7 天过期自动标记 `expired`，不会无限堆积。

## 三、自动向量化

记忆写进 `memory_records` 后，需要被向量化才能做语义检索。

### 技术选型

- **Embedding 模型**：BAAI/bge-m3（1024 维）
- **向量存储**：pgvector 扩展（PostgreSQL 原生支持）
- **向量表**：`memory_embeddings`，外键关联 `memory_records`

### 自动化机制

两层保障：
1. **DB Trigger**：`memory_records` 表的 INSERT / UPDATE 事件自动触发 Edge Function `embed-memory`，实时向量化
2. **pg_cron 兜底**：每 20 分钟扫描一次，补漏 trigger 失败的记录

### 哪些不向量化

- `identity_core`（AI 人格定义）——固定全量注入，不需要检索
- `profile_core`（用户核心档案）——同上
- `raw_events`（对话原文层）——体量太大，向量化成本不划算，靠关键词检索

---

## 四、混合召回

检索是记忆系统的核心。纯关键词搜会漏语义相近但用词不同的记忆，纯向量搜对精确匹配（人名、日期）反而不如关键词。所以用双路混合：

### 双路召回

```
用户最新消息
    ├─→ 关键词路 (pg_trgm word_similarity)
    │       → 命中精确匹配（人名、地点、专有名词）
    │
    └─→ 向量路 (pgvector cosine similarity)
            → 命中语义相关（同义表述、模糊回忆）
            
    两路结果 → 分数融合 → 去重 → 返回 top-N
```

### 多子查询并发（E+ 方案）

用户的消息经常很长，包含多个话题。如果只用整条消息做一次检索，会偏向其中某个话题。

解决方案：把长消息**按标点切分成多个子查询**，每个子查询独立做向量检索，结果合并去重。这样每个话题都有机会召回对应的记忆。

### 召回注入

召回的记忆以独立文本块追加到系统提示词末尾（不是插入对话历史里），这样：
- 不会破坏对话的自然流
- 模型知道这是「想起来的」背景信息，而不是刚说过的话

---

## 五、防幻觉门控（核心亮点）

这是整套系统里我花时间最多、也最有产品价值的一块。

### 为什么需要门控

最朴素的 RAG 是「检索 top-k → 塞进上下文 → 让模型自己用」。但在陪伴场景这会出事：

检索回来的记忆和当前问题只是「沾点边」时，模型会把它当成确定事实，脑补出用户没说过的话。对陪伴产品来说，**一次编造就能击穿信任**。

### 三档证据裁决

门控实现为一个 Supabase Edge Function（TypeScript），核心逻辑：

**Step 1：查询意图分类**

先判断用户这句话在问什么类型的问题：

| 类型 | 例子 | 门控策略 |
|---|---|---|
| 情绪 | 「你想我吗」 | 宽松（情绪表达不需要事实验证） |
| 身份 | 「你叫什么」 | 走固定身份表，不走检索 |
| 事实 | 「我上次说我老家哪里」 | **严格三档裁决** |
| 通用 | 「今天天气怎么样」 | 正常回答 |

**Step 2：对事实类查询，做证据裁决**

```
检索结果
    ↓
计算两个信号：
  1. word_similarity（关键词命中度）
  2. 向量 cosine similarity（语义相关度）
    ↓
双信号综合评分
    ↓
┌─ 评分高 → strong（强证据）→ 直接采信，直答
├─ 评分中 → weak（弱证据）→ 附上原文片段，让模型自己判断
└─ 评分低 / 无命中 → none（无证据）→ 强制回答「我不确定」
```

### 核心取舍：召回率 vs 准确率

这是一次典型的权衡。多召回意味着更「知情」，但也更容易带进噪声、诱发幻觉。

**我在陪伴场景明确选了准确率优先**——宁可少说、不说，也不能编造。因为陪伴关系里，「你为什么记错了」的伤害，远大于「你怎么没记住」。

### 敏感信息拦截（secret_trap）

单独设了一道硬闸：对密码、证件号、银行卡号这类查询，**无条件拒答**，无论检索到什么。

这是防「用套话把隐私问出来」的安全底线，不参与上面的三档逻辑，直接拦。

### 泛词过滤

有些查询词太泛（「那个」「之前的」），命中一堆不相关的记忆，干扰裁决。门控内维护一份泛词表（v_stop），遇到这些词会降权处理，避免因为「沾了一个常见词」就误判为强证据。

泛词表不是一次写死的——靠每周审计日志持续收敛。

### 门控质量闭环

门控好不好，不能靠「我聊两句感觉还行」。所以建了两套机制：

**1. 金问题集（发布门禁）**

20 条有代表性的测试问题，覆盖情绪、身份、事实、隐私钓鱼各类。
每次改门控代码后，**必须先跑这 20 条回归测试，全通过才允许上线**。一条红了就不许发布。

**2. 每周审计日志**

门控每次裁决都会写日志到 `memory_gate_log` 表：

```
query         -- 用户问了什么
query_type    -- 意图分类
gate          -- 裁决结果（strong/weak/none）
no_evidence   -- 是否无证据
best_ws       -- 最佳关键词匹配分
best_vec      -- 最佳向量匹配分
created_at    -- 时间戳
```

每周定时审计这些日志，重点看两类错误：
- **误杀**：该答的被 none 拦了（泛词表太激进 / 评分阈值太高）
- **漏网**：该拦的被 strong 放过了（相似度计算有漏洞）

发现问题后调泛词表或阈值，然后**再跑金问题集确认没引入新问题**，形成闭环。

## 六、事实层（raw_events）

除了精选记忆，还有一层「原文层」——对话原文全量存储。

| 特性 | 说明 |
|---|---|
| 表名 | `raw_events` |
| 去重 | message_id 主键去重 |
| 索引 | pg_trgm（关键词模糊搜索）|
| 向量化 | 不做（体量太大，成本不划算）|
| 用途 | 当精选记忆找不到时的兜底检索 |

它和 `memory_records` 的关系：
- `memory_records` 是**精选层**——少而精，全部向量化，召回质量高
- `raw_events` 是**原文层**——全而杂，只有关键词索引，用来兜底和回溯

这样的两层设计让系统既有高质量的语义检索能力，又不会因为「刚好没选进精选」就彻底丢失某段对话。

```
                          ┌──────────────────────────────────┐
                          │          对话客户端               │
                          └──────────────┬───────────────────┘
                                         │
               ┌─────────────────────────┼─────────────────────────┐
               │ 写入路径                  │                         │ 读取路径
               ▼                          │                         ▼
  ┌──────────────────────┐               │            ┌──────────────────────────┐
  │  记忆写入              │               │            │  混合召回                  │
  │  手动标记              │               │            │                          │
  │  + 摘要器(审核后写入)   │               │            │  ┌─ 关键词路 (pg_trgm)     │
  └──────────┬───────────┘               │            │  └─ 向量路   (pgvector)    │
             │                            │            │  → 分数融合 → top-N        │
             ▼                            │            └─────────────┬────────────┘
  ┌──────────────────────┐               │                          │
  │  自动向量化            │               │                          ▼
  │  bge-m3 (1024维)      │               │            ┌──────────────────────────┐
  │  DB Trigger + cron    │               │            │  防幻觉门控                │
  └──────────────────────┘               │            │  意图分类                  │
                                          │            │  → 三档裁决                │
             ┌────────────────────────────┘            │    strong / weak / none    │
             │                                          │  + secret_trap            │
             ▼                                          └─────────────┬────────────┘
  ┌──────────────────────┐                                            │
  │  raw_events (原文层)  │                                            ▼
  │  全量存储 + trgm索引   │◄─── 兜底检索 ────   ┌────────────────────────────────┐
  └──────────────────────┘                      │  注入对话上下文                 │
                                                 │  （经门控过滤后的可信记忆）       │
                                                 └────────────────────────────────┘
```
