## L-001 · 有证据幻觉（细节错配）

**状态**：🔴 未解 · 记录于 2026-09

### 现象

模型基于一条**真实存在**的记忆生成回复，但把记忆里的某个细节搞错了。不是凭空编造，是「有中生错」。

真实案例：记忆库里存了「某药物，口服，每日两次」。模型要生成用药提醒时，把「口服」说成了「点（滴眼）」——因为记忆库里同时存在另一种「滴眼液」类药物，两条记忆的细节被错误拼接了。

### 为什么现有门控防不住

现有的防幻觉门控（见 [gate-implementation](../examples/gate-implementation.md)）解决的是**「无证据幻觉」**——库里没有依据时，强制模型承认「不确定」。

但这次的情况是：

1. **门控根本没上场**——它挂在「用户查询 → 检索 → 裁决」链路上，而这次错误发生在模型主动生成回复时，不是查询触发的。
2. **就算上场也会放行**——因为「该记忆确实存在」，门控会判定为强证据（strong）、正常放行。它判断得没错。问题出在放行**之后**：模型在正确的记忆上加工出了错误细节。

**根本原因**：门控把整条记忆当作一坨文本，只判断「有没有关系」，看不见文本内部的字段。「口服」和「滴眼」在它眼里都只是字符，分不清给药方式的差异。

### 解决思路（待实现）

对高风险记忆做**结构化字段抽取 + 生成时的实体一致性校验**。

不再把关键事实存成一句自然语言，而是拆成结构化字段：

```json
{
  "type": "medication",
  "name": "某药物",
  "route": "口服",
  "frequency": "每日两次",
  "fasting": true
}
```

这样当模型生成涉及该事实的回复时，系统可以拿结构化字段去校验生成内容——比如提到给药方式，就对比 `route` 字段，说错了当场拦下。

这在 RAG 领域属于**结构化事实抽取 + 实体一致性校验（entity consistency check）**的范畴。

### 适用范围（不是所有记忆都要结构化）

只对**细节错配代价高**的记忆做，比如：

- 药物（给药方式、剂量、频次）
- 日期 / 数字（金额、计数、时间点）
- 专有名词（人名、型号、账号形式）

情绪类、叙事类记忆不需要——它们本来就没有「必须精确」的字段。

### 一句话总结

> 现有门控治的是「无中生有」（凭空编造），下一步要治的是「有中生错」（事实存在但细节错配）。前者靠证据裁决，后者靠字段级一致性校验。这是两类不同的幻觉，需要两套机制。
