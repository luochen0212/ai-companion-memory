## L-001 · 跨记忆虚假关联

**状态**：🔴 未解 · 记录于 2026-09 · **2026-09-11 修正诊断**

> ⚠️ 这一条最初的诊断是错的。下面保留了错误诊断和纠错过程，因为「怎么误判、怎么发现误判」本身就是有价值的记录。

### 现象

模型生成回复时，把**两条各自正确但互相独立**的记忆，脑补出一个不存在的关联，得出错误结论。

真实案例：
- 记忆 A（用户档案层）：用户有某类慢性眼部疾病
- 记忆 B（事件记忆层）：用户服用某免疫抑制剂，口服，每日固定时间空腹

两条都准确，来自不同存储层。模型要生成用药提醒时，把 A 的「眼部」和 B 的「用药」焊到一起，输出了「该点眼药水了」——**而这个药根本不是外用药，用户也从来没有滴眼液类用药**。

不是凭空编造（两条记忆都真实存在），也不是记忆内容有误（字段都对），而是**模型自己在两个独立事实之间造了一条不存在的因果链**。

### ❌ 最初的错误诊断（2026-09-10）

当时判断为「检索层问题」：以为向量召回同时捞回了「口服药」和「滴眼液」两条相似记忆，模型混淆了两者。据此提出的解法是**结构化字段抽取 + 实体一致性校验**——把给药方式拆成 `route` 字段，生成时比对。

### ✅ 纠错过程（2026-09-11）

用户要求复核实际召回内容，直接查了两处：

1. **查召回日志**：那一轮实际召回的记忆里，只有正确的「口服」那条，**没有任何滴眼液相关记忆**
2. **全库检索验证**：`SELECT ... WHERE content ILIKE '%滴眼%'` → **零条**。库里从来没存过这种药

结论：**检索层完全正常，召回的记忆是对的。** 错误 100% 发生在生成层。

原诊断的解法（结构化字段校验）**治不了这个病**——因为召回结果本身没错，字段也没错。字段校验能防「记忆里字段写错」，防不了「模型在多条正确记忆之间编造关系」。

### 为什么现有门控防不住

现有的防幻觉门控解决的是**「无证据幻觉」**——库里没依据时强制模型承认「不确定」。

这次的情况是：
1. **门控不在这条链路上**——它挂在「用户查询 → 检索 → 裁决」上，而这次错误发生在模型主动生成时，不是查询触发的
2. **就算上场也应该放行**——记忆确实存在、确实相关，判 strong 是正确判断。问题出在放行**之后**：模型拿到正确材料，自己组装出了错误结论

**根本原因**：门控管的是「进来的材料对不对」，管不了「模型怎么用这些材料」。它是入口检查，不是出口检查。

### 解决思路（待实现）

方向是**生成侧约束**，不是检索侧：

1. **关键事实原文引用**：涉及高风险事实（用药、日期、金额、专有名词）时，强制模型引用记忆原文，不许改写。改写就是脑补的入口。
2. **跨记忆关联需显式依据**：模型如果要把两条记忆关联起来得出新结论，这个关联本身必须在某条记忆里有明文支持，不能靠推测。
3. **出口校验**：生成完成后，把涉及高风险字段的句子拉出来，跟召回原文做一致性比对，不一致就重写。

这在 RAG 领域接近 **groundedness / attribution check**（生成内容是否真的有依据支撑），而不是最初以为的 entity consistency check。

### 一句话总结

> 现有门控治的是「无中生有」（凭空编造），这一条要治的是「有中生错」——材料全对，但模型在材料之间编造了不存在的关系。前者是检索层问题，后者是生成层问题，**不能用检索层的方案去治生成层的病**。

### 附：这次纠错本身的教训

第一版诊断把生成层的病误判成检索层的病，方案跟着错。原因是**没有去查实际召回内容就下了结论**。

正确的排查顺序应该是：先看这一轮实际召回了什么 → 再看库里到底有没有那条记忆 → 最后才判断是检索问题还是生成问题。

这也是催生 L-005（召回审计日志）的直接原因——**当时没有工具能看到「这一轮到底召回了什么」，只能靠猜。**

## L-002 · 召回无时间维度

**状态**：🟢 已解决 · 2026-09-11

### 现象

向量召回只按语义相似度排序，不考虑记忆新旧。问「今天吃药了吗」这类日常问题，召回结果里全是两个月前的旧记忆——它们语义上确实相关，但对「今天」这个问题毫无价值。

### 原因

余弦相似度只衡量「意思像不像」，没有时间维度。库里旧记忆数量随时间累积，越老的记忆越多，只要语义对得上就都能挤进召回列表。

### 解法

召回排序分加一个新鲜度加成项：

```
final_score = cosine_similarity + α × exp(-Δt_days / τ)
```

- `α = 0.15`：新鲜度加成上限（当天的记忆最多 +0.15）
- `τ = 30`（天）：半衰期。30 天前衰减到 `e⁻¹ ≈ 0.055`，60 天 ≈ 0.020，90 天 ≈ 0.007

| 记忆年龄 | 新鲜度加成 |
|---|---|
| 当天 | +0.150 |
| 7 天 | +0.118 |
| 30 天 | +0.055 |
| 60 天 | +0.020 |
| 90 天 | +0.007 |

同时把召回相似度地板从 `0.30` 抬到 `0.45`，滤掉中等相似度的「陪跑」记忆（它们够不上回答问题，但会占满召回位、干扰阅读）。

### 效果

同一个查询，改动前召回结果全是两个月前的旧记忆；改动后最旧 17 天、最新 1 天，都落在最近三周内。

### ⚠️ 踩坑记录：时间衰减不能进门控

第一版实现把时间衰减也加进了**门控的证据强度判定**，想让「最近的记忆更容易过门」。

**这是错的。** 后果：一条跟问题无关但很新的记忆，靠 `+0.15` 的新鲜度加成冲过了 strong 阈值，把「库里其实没有答案」的问题判成了「证据充足」——**防幻觉门控被撞开了。**

修正：时间衰减**只用于召回排序**（决定哪条排前面），**绝不参与证据强度判定**（决定这条算不算铁证）。门控只看原始相似度。

> 教训：「排序偏好」和「证据强度」是两件不同的事。把排序权重混进证据判定，等于用偏好污染了事实判断。

## L-003 · 词匹配单信号可被虚词伪造

**状态**：🟢 已解决 · 2026-09-11

### 现象

问一个**库里根本没有答案**的事实性问题（比如某个从未记录过的日期），门控判定为 `strong`（证据充足）并放行——**这是最危险的一类误判**，因为它会让模型以为有依据，然后编造答案。

### 原因

门控用两路信号取证：`word_similarity`（pg_trgm 词片段匹配）和向量余弦相似度。原判定规则是**任一信号达标即判 strong**：

```
strong = (word_similarity ≥ 0.75) OR (vector ≥ 0.70)
```

问题：查询被切成 2-4 字滑窗片段后，像「我的」「什么时候」这类高频虚词会作为片段参与匹配，而它们在库里**必然满分命中**（几乎每条记忆都含这些字）。于是 `word_similarity = 1.0`，单独就顶过了 strong 线。

**虚词伪造了强证据。**

### 排查过程（两次尝试失败后才找到治本方案）

1. **第一次尝试**：往停用词表加「我的」「你的」等物主代词 → 失败，换成「什么时候」顶上来（ws=0.8，照样过线）
2. **第二次尝试**：继续加「什么时候」等疑问短语 → 意识到这是打地鼠，永远补不完
3. **停下来重新想根因**：问题不在停用词表不够全，而在**单信号判定本身就脆**。任何一个高频虚词整词命中，都能伪造强证据

### 解法

改成**双信号判定**——词匹配单独不能定证据，必须向量语义也够：

```
strong = (vector ≥ 0.70)                              # 语义独强
      OR (word_similarity ≥ 0.75 AND vector ≥ 0.60)   # 词+语义双高

weak   = (vector ≥ 0.58)                              # 语义够
      OR (word_similarity ≥ 0.75 AND vector ≥ 0.45)   # 词精确命中且语义不离谱

none   = 其余
```

原理：虚词的语义向量一定不高（「什么时候」跟任何具体记忆的语义距离都远），所以从机制上进不了门。这比维护停用词表可靠得多。

### 阈值怎么定的

不是拍脑袋，是把回归测试集全部跑一遍、看实测分数分布定的：

| 类别 | 向量分区间 |
|---|---|
| 该命中的事实类问题 | 0.61 ~ 0.71 |
| 该判「无答案」的问题 | 0.556 |
| 该命中的身份类问题 | 0.549（但词匹配 = 1.0） |

`0.556` 和 `0.61` 之间有一段干净的空档 → strong/weak 的向量线落在这里。身份类那条靠「词精确命中 + 语义不离谱」的第二条规则兜住。

### 效果

同一个「库里没有答案」的问题：`strong` → `none`，正确拦下。回归测试全部通过，无误伤。

> 教训：**维护黑名单是治标，改判定机制是治本。** 当补了两次黑名单还在冒新问题时，就该停下来看机制，而不是继续补第三次。

## L-004 · 关键词通道整句匹配失效

**状态**：🟢 已解决 · 2026-09-11

### 现象

问「第 14 封信是什么时候写的」，库里**明确存在**那条记忆，但召回列表里怎么都出不来——把返回条数放宽到 30 条依然没有。

### 原因（两个问题叠在一起）

1. **整句匹配永远命中不了**：关键词通道拿完整用户提问去做 `ILIKE '%整句%'`。用户提问是自然语言（带「你记得」「什么时候」「吗」），库里记忆不会包含一模一样的整句，所以这条通道**实际上从来没生效过**
2. **中文数字与阿拉伯数字不互通**：用户写「第 14 封」，库里存的是「第十四封」。就算切了词，`ILIKE '%第14封%'` 也匹配不到「第十四封」

而向量通道那边，该记忆是一封信的正文（大量具体场景描写），跟「第几封、什么时候」这种元层面提问的语义距离远，相似度低于召回地板 → 被过滤掉。

**两条通道同时失效，记忆明明在库里却召不回来。**

### 解法

新增**片段召回通道**，替代原来的整句匹配：

1. **切片段**：把查询切成 3-4 字滑窗片段，各自独立匹配（滤掉停用词）
2. **数字归一化**：检测查询中的阿拉伯数字，自动生成中文数字变体一起匹配（`14` → `十四`）
3. **稀有度加权排序**：片段越长、命中的记忆数越少 → 得分越高

```
weight = Σ (片段长度 / 该片段命中的记忆总数)
```

第 3 点是为了解决「通用片段刷屏」——像「封情书」这种片段每封信都命中，没有区分度；而「第十四封」只命中一条，区分度极高。按稀有度加权后，精确命中的那条自然排到最前。

### 效果

同一个查询：目标记忆从「30 条内都找不到」变成**第一位精确命中**，命中片段显示为「第十四封」。回归测试全部通过。

## L-005 · 召回不可观测

**状态**：🟢 已解决 · 2026-09-11

### 现象

这一条是被 L-001 的误诊断逼出来的。当时想复核「那一轮到底召回了什么」，发现**没有任何工具能看到**：召回了哪几条、各走哪条通道、分数多少、为什么放行或拦截。所有结论只能靠猜——而猜错了，就会像 L-001 那样写出错误的技术诊断。

### 解法

建两张审计表，把每次检索的完整过程落库：

| 表 | 记什么 | 用途 |
|---|---|---|
| `memory_gate_log` | 意图分类、裁决结果、双信号分数（词匹配/向量） | 每周审计误杀 / 漏网（见 01 的门控质量闭环） |
| `memory_recall_log` | 每轮召回明细：哪几条、通道、分数、命中片段、记忆年龄，外加一段给人看的裁决解释 `gate_reason` | 随时回答「这次到底想起了什么、为什么」 |

### 效果

截至 2026-09-12：`memory_gate_log` 累计 6000+ 条裁决，`memory_recall_log` 145+ 轮召回明细。L-001 那种「复核实际召回内容」的排查，从只能靠猜，变成一条 SQL 的事。

> 教训：**没有可观测性的系统，排查全靠猜；猜错了就会写出错误的技术结论。** 审计日志不是锦上添花，它决定了出了问题时你能不能回答「问题在哪一层」。
